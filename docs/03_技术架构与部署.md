# ChatServer 技术架构与部署手册

> 产品设计视角 · 技术栈、系统架构、性能表现与部署运维
> **说明**：基于当前代码实现核对后整理（未改动源码）。架构决策均标注最终确定版，并说明 QClaw 奠基（💡）与 WorkBuddy 定稿（🔧）的分工。

## 一、技术栈（最终确定版）

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Rust（edition 2021） | 高并发、内存安全、低延迟 |
| Web 框架 | Axum 0.7 + Tokio | 异步运行时，零成本抽象 |
| 数据库驱动 | sqlx 0.8（`AnyPool` 多库抽象） | 当前以 MySQL 8.4 为唯一验证后端 |
| 关系数据库 | MySQL 8.4 | 业务主存储 |
| 缓存 / 分布式 | Redis | 分布式限流、状态预留 |
| 认证 | jsonwebtoken (JWT HS256) | Access + Refresh 双 Token |
| 密码哈希 | Argon2id（可调档） | 旧 SHA256/bcrypt 哈希透明迁移 |
| 实时通道 | axum WebSocket | 全双工长连接 |
| 可观测 | tracing | 结构化日志 |
| ID 生成 | 自研 Snowflake | 规避线上 `messages.id` 无自增约束 |

## 二、系统架构

```
                         ┌─────────────────────────────┐
   客户端 (Web/App) ───► │        ChatServer (Rust)      │
                         │                              │
    REST API ──────────► │  Router (Axum)               │
                         │   ├─ Auth / Friends / Msgs    │
                         │   ├─ Groups / Search          │
                         │   └─ Monitor (health/status)  │
                         │                              │
    WebSocket ─────────► │  WS Gateway                  │
                         │   ├─ 多端连接管理             │
                         │   └─ push_to_user/group       │
                         │                              │
                         │  Middleware                  │
                         │   ├─ CORS / AuthUser          │
                         │   └─ Rate Limit (Redis+Memory) │
                         └──────┬───────────┬───────────┘
                                │           │
                          ┌─────▼────┐ ┌────▼─────┐
                          │  MySQL   │ │  Redis   │
                          │(AnyPool  │ │(限流/    │
                          │ 读写分离) │ │ 状态)    │
                          └──────────┘ └──────────┘
```

### 2.1 关键架构决策（最终确定版）

1. **读写连接池分离（🔧 定稿）**：读池（300）与写池（500）独立、共享底层连接（sqlx `Arc`），写并发经信号量（容量 = 写池 500）控制，避免慢写拖垮读路径或超卖连接。
2. **消息异步批量写入（🔧 定稿）**：`MESSAGE_ASYNC=1` 时，消息先入内存通道，后台 3 worker 每 50ms / 500 条批量事务落库，规避 `innodb_flush_log_at_trx_commit=1` 的逐条 fsync 瓶颈。
3. **REST + WS 共享推送**：单聊/群聊推送统一经过 `push_to_user` / `push_to_group`，保证多渠道一致。
4. **多端在线模型**：`uid → {conn_id → Sender}`，设备级隔离，断线不影响其他设备。
5. **分布式就绪**：`AnyPool` 多库抽象 + Redis 限流/状态抽象，预留水平扩展能力（实例间 WS 路由待补）。

## 三、性能表现（实测）

> 以下为 2026-10-09 在本机（12 核 / MySQL 8.4 / 连接池上限 800）的压测结果，由 WorkBuddy 执行。

### 3.1 完整链路 10K 并发（注册 + 登录 + 发消息）

| 并发 | 注册成功率 | 登录成功率 | 发消息成功率 | 发消息 QPS |
|---|---|---|---|---|
| 500 | 100% | 100% | 100% | ~3,900 |
| 1000 | 100% | 100% | 100% | ~3,800 |
| 2000 | 100% | 100% | 100% | ~4,100 |
| 5000 | 100% | 100% | 100% | ~3,700 |
| 8000 | 100% | 100% | 100% | ~3,400 |
| 10000 | 100% | 100% | 100% | ~3,300 |

### 3.2 关键指标
- 预注册 12,000 用户：~54 秒
- 注册 10K 并发 p99：~15.4s（Argon2id CPU 密集型，属安全设计的合理代价）
- 登录 10K 并发 p99：~16.8s
- 发消息 10K 并发 p99：~2.7s
- 压测后连接池：`read_in_use=0`，**零泄漏**

### 3.3 功能回归
- 冒烟测试：46/46 通过
- WebSocket 端到端：11/11 通过（含 35s 长连接存活）

## 四、部署与运维

### 4.1 环境依赖
- Rust 工具链（stable）
- MySQL 8.4（建议 `max_connections ≥ 1000`）
- Redis（可选，用于分布式限流；缺失时降级为内存限流）

### 4.2 配置要点（config.yaml 最终版）
```yaml
server:
  host: "0.0.0.0"
  port: 18080          # 当前避本机代理占用 8080 的临时端口
database:
  max_total_connections: 800
  read_pool_max: 300
  write_pool_max: 500
jwt:
  access_token_expire_minutes: 120
  refresh_token_expire_days: 7
rate_limit:
  enabled: false
  requests_per_minute: 100000
```

### 4.3 启动方式
```bash
# 关闭本地 HTTP 代理干扰（本机存在 HTTP_PROXY 环境变量）
unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy

# 提高限流上限 + 开启异步消息写入
RATE_LIMIT_RPM=100000 MESSAGE_ASYNC=1 \
  ./target/chat_server
```
> 说明：当前监听端口为 **18080**（避开本机 8080 被本地代理占用的情况）。生产可改回 8080 或将代理排除本机地址。

### 4.4 运维接口
| 接口 | 用途 |
|---|---|
| `GET /health` | 健康检查探针 |
| `GET /status` | 连接池、在线数、信号量状态 |
| `GET /api/ws/stats` | WebSocket 连接统计 |

### 4.5 关键环境变量
| 变量 | 作用 |
|---|---|
| `RATE_LIMIT_RPM` | 覆盖限流阈值（压测放开） |
| `MESSAGE_ASYNC=1` | 启用消息异步批量写入 |
| `ARGON2_MODE=secure` | 提升密码哈希安全档 |
| `REDIS_URL` | 指定 Redis 地址 |
