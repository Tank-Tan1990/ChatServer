## 二、设计理念（双工具协作视角）

ChatServer 的设计理念由两个阶段共同塑造，二者前后衔接、互为补充。

### 2.1 QClaw 奠基的设计理念（2026-04）
- **异步优先**：Rust + Tokio + Axum 全异步栈，单进程高并发处理请求与长连接。
- **模块化分层**：`api / ws / db / redis / state / middleware / monitor` 职责清晰，便于演进。
- **JWT 双 Token 体系**：Access Token（2h）用于业务鉴权，Refresh Token（7d）用于续期，提供 Token 黑名单吊销思路。
- **WebSocket 实时通信**：连接鉴权 + 30s 心跳保活 + Redis 在线状态（TTL 5 分钟），奠定实时推送基础。
- **多数据库抽象构想**：以 `DatabaseType` + `SqlDialect` + `AnyPool` 统一包装，意图一套代码适配多种关系库。
- **读写分离连接池**：读池 / 写池分离 + 写并发信号量 + 后台写队列的架构尝试。
- **分布式部署蓝图**：Nginx/HAProxy 负载均衡 → 多实例 → Redis（状态）+ MySQL（数据）的水平扩展目标。

### 2.2 WorkBuddy 演进的工程理念（2026-09～10）
- **压测驱动**：以"10K 并发 100% 成功"为硬目标，分阶段（500→10000）量化验证，用数据定位瓶颈而非凭直觉。
- **连接池配置化与缩放**：把硬编码上限改为配置驱动，并按 `max_connections` 的 80% 自动缩放，杜绝超卖。
- **安全与性能可权衡**：密码哈希采用 Argon2id 并可调档（默认档优先性能、安全档按需开启），旧哈希透明迁移。
- **写路径削峰**：消息异步批量写入（内存队列 + 后台多 worker 事务批量落库），把 N 次 fsync 压缩为 1 次。
- **稳定性优先**：统一 `push_to_user/group` 推送链路、修复 `messages.id` 无自增的写入失败、补齐多端在线模型。
- **可观测性**：连接池 `in_use/idle`、信号量余量、WebSocket 在线数成为定位泄漏与瓶颈的一手指标。

### 2.3 两个工具协作的闭环
> QClaw 完成了"从 0 到 1"的功能骨架与架构构想；WorkBuddy 以 10K 并发为靶心，完成了"从能用到达标"的性能定稿与缺陷修复。二者共同构成当前可运行的 ChatServer。

| 阶段 | 工具 | 主要产出 |
|---|---|---|
| 2026-04 | QClaw | 全模块功能 CRUD、REST/WS 骨架、JWT 双 Token、多库抽象层、部署蓝图、10K 压测方法论与测试脚本 |
| 2026-09～10 | WorkBuddy | 连接池配置化（800）、Argon2id 可调、消息异步批量写入、WS 推送 Snowflake 修复、10K 全链路验证（注册+登录+消息 100%） |
| 全程 | 共享 | 源码（Rust 工程）、`docs/` 文档、`tests/` 压测脚本 |

## 五、核心设计原则（最终确定版）

1. **REST + WebSocket 双通道**：请求/响应类用 HTTP，实时消息用 WebSocket，二者共享同一推送链路（`push_to_user` / `push_to_group`）。
2. **多端在线友好**：同一用户可在手机、PC 等多设备同时在线，设备级隔离、互不影响。
3. **安全与性能可权衡**：密码采用 Argon2id 哈希（可调档），旧哈希格式透明迁移；JWT 双 Token 机制。
4. **高并发导向**：连接池配置化（读 300 / 写 500 / 总 800）、写并发信号量、消息异步批量写入、限流与可观测性内建。
5. **可水平扩展**：基于 `AnyPool` 多库抽象 + Redis 状态/限流抽象，预留多实例部署能力（实例间 WS 路由待补）。
