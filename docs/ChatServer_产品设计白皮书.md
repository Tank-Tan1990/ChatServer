## 1. 产品概述

### 1.1 产品定位

ChatServer 是一套**开箱即用的即时通讯后端能力底座**。它将"账号体系、好友关系、单聊/群聊、实时消息推送、全局搜索"等 IM 核心能力封装为标准化 RESTful API 与 WebSocket 实时通道，让业务方无需从零自研通信层，即可在自有产品中快速嵌入聊天能力。其工程定位是**稳定支撑万级并发长连接**的中台型基础设施。

### 1.2 要解决的问题与价值主张

| 痛点 | ChatServer 的价值 |
|---|---|
| 自建 IM 成本高、周期长（长连接、消息可靠性、并发模型均需专业积累） | 提供完整 IM 能力集，业务方聚焦自身场景，通信层开箱即用 |
| 并发上来后连接池耗尽、消息堆积、推送抖动 | 读写池分离 + 写并发信号量 + 消息异步批量落库，10K 并发链路 100% 成功 |
| 多端登录互踢、离线消息丢失 | 多端在线模型（设备级隔离）+ 历史消息补偿拉取 |
| 密码安全与合规 | Argon2id 可调档哈希、JWT 双 Token、旧哈希透明迁移 |
| 运维黑盒、瓶颈难定位 | 内置 `/status` 连接池/信号量观测、`/health` 探针、结构化日志 |

### 1.3 目标用户与典型场景

- **目标用户**：需要自建即时通讯能力的业务方、企业内部协作系统、社交/社区类产品的后台团队。
- **典型场景**：
  - 企业内部 IM / 办公协同（单聊 + 群聊 + 组织内搜索）
  - 社区 / 电商 App 的客服与私信
  - SaaS 产品内嵌的实时通知与对话
  - 作为更大系统的通信中台，对外提供消息能力

### 1.4 产品边界

**做**：账号认证、好友关系、单聊/群聊、实时推送、搜索、运维可观测。
**当前不做（规划中）**：离线消息主动补偿推送、消息撤回/编辑、群公告与管理员角色、找回/修改密码、跨实例 WS 路由（多实例水平扩展）、第三方登录/双因子。

### 1.5 核心差异化

- **并发优先的工程实现**：以"10K 并发 100% 成功"为硬指标驱动设计，而非功能堆叠。
- **双通道一致**：REST 与 WebSocket 共用同一推送链路，多渠道语义统一。
- **安全与性能可权衡**：密码哈希分档、登录校验隔离于业务线程，兼顾安全与吞吐。
- **可水平扩展基座**：多库抽象 + Redis 状态抽象，为分布式部署预留接口。

## 3. 功能设计详述

> 每一模块给出**用户故事（产品视角）**、**设计要点（确定版）**、**关键接口**。角色定义：普通用户（C）、系统（S）。

### 3.1 账号与认证（Account & Auth）

**用户故事**
- 作为新用户，我希望用用户名+密码注册账号，以便使用聊天服务。
- 作为注册用户，我希望登录后获得凭证，并在凭证过期前免重复登录。
- 作为登录用户，我希望在任一设备登出后，该设备的刷新凭证失效，保障账号安全。

**功能点**
| 编号 | 功能 | 优先级 | 状态 |
|---|---|---|---|
| A-01 | 注册（用户名+密码+昵称） | P0 | ✅ 已实现 |
| A-02 | 登录（签发双 Token） | P0 | ✅ 已实现 |
| A-03 | Access Token 刷新 | P0 | ✅ 已实现 |
| A-04 | 登出（失效 Refresh Token） | P0 | ✅ 已实现 |
| A-05 | 当前用户信息 | P0 | ✅ 已实现 |
| A-06 | 密码安全存储（Argon2id + 旧哈希迁移） | P0 | ✅ 已实现 |
| A-07/A-08 | 第三方登录 / 找回·修改密码 | P2 | ⚪ 规划中 |

**设计要点（确定版）**
- **JWT 双 Token**：Access Token（2h）用于业务鉴权，Refresh Token（7d）用于续期；响应为顶层 `{token, refresh_token}`。
- **凭证双形态**：`Authorization: Bearer` 与 `?token=` 并存，兼容旧客户端。
- **密码安全**：Argon2id 哈希（默认性能档 `m=7MiB,t=1,p=1`，`ARGON2_MODE=secure` 升档）；历史哈希在首次登录成功后自动重哈希为 Argon2id（透明迁移）。
- **登录不阻塞**：密码校验为 CPU 密集型，置于 `spawn_blocking` + 信号量（默认 300）中，避免拖垮异步工作线程。

### 3.2 好友关系（Friendship）

**用户故事**
- 作为用户，我想搜索并申请添加好友，建立我的社交连接。
- 作为被申请方，我想查看申请列表并同意/拒绝，同意后双方互为好友。

**功能点**：好友列表（F-01）、发起申请（F-02）、申请列表（F-03）、处理申请（F-04）、删除好友（F-05）；好友备注/分组（F-06）规划中。

**设计要点**：双向确认模型；处理入参为 `request_id` + `accept`（布尔）。

### 3.3 消息系统（Messaging）

**用户故事**
- 作为用户，我想给好友或群组发送文字消息，并实时看到对方收到。
- 作为用户，我想回溯历史会话，并知道哪些消息未读。

**功能点**
| 编号 | 功能 | 优先级 | 状态 |
|---|---|---|---|
| M-01 | 历史消息（分页） | P0 | ✅ |
| M-02 | 发送消息（REST + WS 双入口） | P0 | ✅ |
| M-03 | 标记已读 | P0 | ✅ |
| M-04 | 未读计数 | P1 | ✅ |
| M-05 | 富媒体消息（文本为主，结构预留） | P2 | 🟡 |
| M-06/M-07 | 撤回/编辑 · 离线补偿推送 | P2/P1 | ⚪/🟡 |

**设计要点**
- 单聊以 `receiver_id`、群聊以 `group_id` 区分，二者互斥。
- 消息 ID 由应用层 **Snowflake** 预生成，规避线上 `messages.id` 无自增约束，REST/WS 双路径统一。
- **写库可切换**：默认同步 INSERT；`MESSAGE_ASYNC=1` 进入异步批量写入（内存队列 + 3 worker，每 50ms/500 条事务批量落库），是万级消息吞吐达标的关键。

### 3.4 群组系统（Groups）

**用户故事**
- 作为用户，我想创建群组并把同事拉进来协作。
- 作为群主，我想管理成员、解散群组；作为成员，我想主动退群。

**功能点**：群列表（G-01）、建群（G-02）、群详情（G-03）、解散（G-04）、加入（G-05）、成员列表（G-06）、添加（G-07）/移除（G-08）成员、退群（G-09）；群公告/管理员角色（G-10）规划中。

**设计要点**：`group_members` 联合主键（group_id+user_id，无 id 列）；解散/退群等多表操作置于事务内；`groups` 为 MySQL 保留字需反引号转义。

### 3.5 搜索能力（Search）

- 用户搜索（S-01）、群组搜索（S-02）：登录后调用，关键词 `keyword` 模糊匹配，结果上限 20 条防全表扫描。

### 3.6 实时通信（WebSocket）

**用户故事**
- 作为在线用户，我希望消息一经发送，对方设备立刻收到（单聊与群聊）。
- 作为多设备用户，我希望手机和电脑同时在线，互不顶替。

**功能点**：WS 鉴权（W-01）、单聊推送（W-02）、群聊广播（W-03）、多端在线（W-04）、心跳（W-05）、认证回执（W-06）、WS 统计（W-07）；离线补偿（W-08）规划中。

**设计要点**
- 连接管理：`uid → {conn_id → Sender}`（参考 OpenIM/WuKongIM 网关层），设备级隔离，断线只移除自身通道。
- 推送链路统一：`push_to_user` / `push_to_group` 被 REST 与 WS 发送共用。
- 协议回执（Pong）与业务推送经独立写出任务，避免 socket 写竞争。

### 3.7 平台与运维（Platform & Ops）

- 健康检查（`/health`）、系统状态（`/status` 暴露连接池 in_use/idle、信号量余量）、接口限流（Redis 滑动窗口 + 内存兜底）、CORS、读写池分离、消息异步批量落库、结构化日志。
- **未接入**：熔断器（`circuit_breaker.rs` 已实现逻辑，未挂 API 层，避免改变请求行为）。

## 4. 非功能性需求（NFR）

### 4.1 性能与容量
- **目标基线**：注册+登录+发消息完整链路，500～10000 并发各档位 **100% 成功**，发消息 QPS ≈ 3,300～4,100。
- **容量规划**：连接池读 300 / 写 500（上限 800，按 MySQL `max_connections` 80% 配置）；写并发信号量容量 = 写池 500。

### 4.2 安全
- 密码 Argon2id 哈希，明文不落库；JWT HS256 双 Token，Refresh Token 可吊销。
- 旧哈希格式登录后透明迁移，无迁移中断窗口。

### 4.3 可用性 / 可靠性
- 优雅关闭（graceful shutdown）；WebSocket 心跳保活；压测后连接池零泄漏（`read_in_use=0`）。
- 已知：离线消息无主动补偿，依赖客户端拉历史获得完整消息。

### 4.4 可扩展性
- `AnyPool` 多库抽象 + Redis 状态/限流抽象，具备多实例部署基础；实例间 WS 路由待补。

### 4.5 可观测性
- `/health`、`/status`、`/api/ws/stats` 三类运维接口；结构化 JSON 日志。

## 5. 技术实现概览

### 5.1 架构总览
```
客户端 ──┬─ REST API ──► Axum Router ──┬─ 业务 Handler
         │                            ├─ Middleware(CORS/Auth/限流)
         └─ WebSocket ──► WS Gateway ──┴─ push_to_user/group
                                       │
                                 ┌─────▼────┐  ┌─────▼────┐
                                 │  MySQL   │  │  Redis   │
                                 │(读写分离) │  │(限流/状态)│
                                 └──────────┘  └──────────┘
```

### 5.2 关键设计决策（含 Why）
1. **读写池分离（Why：避免慢写拖垮读路径、杜绝连接超卖）**——读 300 / 写 500，共享底层连接，写经信号量限并发。
2. **消息异步批量写入（Why：规避 `innodb_flush_log_at_trx_commit=1` 逐条 fsync 瓶颈）**——N 次 fsync 压缩为 1 次。
3. **REST+WS 共享推送（Why：保证多渠道语义一致）**。
4. **多端在线模型（Why：手机/PC 不互踢）**。
5. **Snowflake 应用层 ID（Why：线上 `messages.id` 无自增）**。

### 5.3 数据模型（确定版）
| 实体 | 关键字段 |
|---|---|
| users | id, username, nickname, password_hash, avatar_url, status |
| friends | id, user_id, friend_id, status |
| friend_requests | id(request_id), from_user_id, to_user_id, status |
| messages | id(Snowflake), sender_id, receiver_id, group_id, content, msg_type, is_read |
| groups | id, name, description, owner_id, avatar_url |
| group_members | group_id, user_id（联合主键，无 id 列） |
| refresh_tokens | id, user_id, token, expires_at |

## 6. 性能验证结果（实测）

> 2026-10-09 本机（12 核 / MySQL 8.4 / 连接池上限 800），由压测脚本驱动。

| 并发 | 注册 | 登录 | 发消息 | 发消息 QPS |
|---|---|---|---|---|
| 500 | 100% | 100% | 100% | ~3,900 |
| 1000 | 100% | 100% | 100% | ~3,800 |
| 2000 | 100% | 100% | 100% | ~4,100 |
| 5000 | 100% | 100% | 100% | ~3,700 |
| 8000 | 100% | 100% | 100% | ~3,400 |
| 10000 | 100% | 100% | 100% | ~3,300 |

补充：预注册 12,000 用户约 54s；10K 发消息 p99 ≈ 2.7s；功能回归冒烟 46/46、WS 端到端 11/11；压测后连接池零泄漏。

## 8. 附录

### 8.1 API 清单（25 个端点）
```
认证:  POST /api/auth/register | /login | /refresh | /logout
用户:  GET  /api/user/info
好友:  GET/POST /api/friends | GET /api/friends/requests
       POST /api/friends/handle | DELETE /api/friends/:id
消息:  GET/POST /api/messages | POST /api/messages/read | GET /api/messages/unread
群组:  GET/POST /api/groups | GET/DELETE /api/groups/:id
       POST /api/groups/:id/join | GET/POST /api/groups/:id/members
       DELETE /api/groups/:id/members/:member_id | POST /api/groups/:id/leave
搜索:  GET /api/search/users | /api/search/groups
实时:  GET /ws | GET /api/ws/stats
运维:  GET /health | /status
```

### 8.2 关键环境变量
| 变量 | 作用 |
|---|---|
| `RATE_LIMIT_RPM` | 覆盖限流阈值（压测放开） |
| `MESSAGE_ASYNC=1` | 启用消息异步批量写入 |
| `ARGON2_MODE=secure` | 密码哈希升档 |
| `REDIS_URL` | 指定 Redis 地址 |

### 8.3 术语
- **双 Token**：Access（短期业务凭证）+ Refresh（长期续期凭证）。
- **多端在线**：同一用户多设备同时连接，设备级隔离。
- **Snowflake ID**：应用层分布式 ID（41bit 时间戳 + 10bit worker + 12bit 序列）。
