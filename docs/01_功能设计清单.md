# ChatServer 功能设计清单

> 产品设计视角 · 全部功能模块与功能点一览
> **来源标注**：💡 QClaw 奠基（2026-04 设计/实现）｜🔧 WorkBuddy 定稿（2026-09～10 性能与缺陷修复）｜🤝 共享演进

本文档以「功能模块 → 功能点」的层级，完整列出 ChatServer 已设计/已实现的功能。每项标注：
- **优先级**：P0（核心必备）/ P1（重要）/ P2（增强）
- **状态**：✅ 已实现并验证 / 🟡 已实现待优化 / ⚪ 已设计未接入
- **来源**：该功能由哪个阶段的工具主导落地

## 一、账号与认证（Account & Auth）

| 编号 | 功能点 | 优先级 | 状态 | 来源 | 端点 / 入口 |
|---|---|---|---|---|---|
| A-01 | 用户注册（用户名 + 密码 + 昵称） | P0 | ✅ | 💡 | `POST /api/auth/register` |
| A-02 | 用户登录（签发双 Token） | P0 | ✅ | 💡 | `POST /api/auth/login` |
| A-03 | Access Token 刷新 | P0 | ✅ | 💡 | `POST /api/auth/refresh` |
| A-04 | 用户登出（失效 Refresh Token） | P0 | ✅ | 💡 | `POST /api/auth/logout` |
| A-05 | 当前用户信息查询 | P0 | ✅ | 💡 | `GET /api/user/info` |
| A-06 | 密码安全存储（Argon2id，旧哈希透明迁移） | P0 | ✅ | 🔧 | 内部 |
| A-07 | 双因子认证 / 第三方登录 | P2 | ⚪ | — | 未设计 |
| A-08 | 修改密码 / 找回密码 | P2 | ⚪ | — | 未实现 |

**设计要点（最终确定版）**
- 认证采用 **JWT 双 Token**：Access Token（2 小时）用于业务鉴权，Refresh Token（7 天）用于续期。
- 客户端可二选一携带凭证：`Authorization: Bearer <token>` 或 URL 参数 `?token=xxx`，兼容旧客户端。
- 密码哈希最终确定采用 **Argon2id**：默认低强度档（`m=7MiB, t=1, p=1`，优先性能），`ARGON2_MODE=secure` 可切至高强度档；历史上以 SHA256 / bcrypt 存储的密码在首次登录成功后**自动重哈希为 Argon2id**，实现旧格式透明迁移。
- 登录密码校验为 CPU 密集型，置于 `spawn_blocking` + 信号量（默认 300 permit）中执行，避免阻塞 Tokio 工作线程；登录态更新、旧哈希迁移改为后台异步，不阻塞响应。

## 三、消息系统（Messaging）

| 编号 | 功能点 | 优先级 | 状态 | 来源 | 端点 / 入口 |
|---|---|---|---|---|---|
| M-01 | 会话消息历史查询（分页） | P0 | ✅ | 💡 | `GET /api/messages` |
| M-02 | 发送消息（单聊 / 群聊，REST + WS 双入口） | P0 | ✅ | 💡 | `POST /api/messages`、`/ws` |
| M-03 | 标记消息已读 | P0 | ✅ | 💡 | `POST /api/messages/read` |
| M-04 | 未读消息计数 | P1 | ✅ | 💡 | `GET /api/messages/unread` |
| M-05 | 消息类型扩展（文本 / 图片 / 文件 / 表情） | P2 | 🟡 | 💡 | 结构预留，当前以 `text` 为主 |
| M-06 | 消息撤回 / 编辑 | P2 | ⚪ | — | 未实现 |
| M-07 | 离线消息推送补偿 | P1 | 🟡 | 💡 | 依赖实时通道，无独立离线落库补偿 |

**设计要点（最终确定版）**
- 消息统一以 `receiver_id`（单聊）或 `group_id`（群聊）区分投递对象；二者互斥。
- 消息 ID 由**应用层 Snowflake 算法**预生成（`src/snowflake.rs`：41bit 时间戳 + 10bit worker + 12bit 序列），规避线上库 `messages.id` 无 `AUTO_INCREMENT` 的约束，REST 与 WS 两条发送路径统一使用。
- 写库策略可切换：默认同步 `INSERT`；`MESSAGE_ASYNC=1` 时进入**异步批量写入**（内存队列 + 后台 3 个 worker 每 50ms / 500 条事务批量落库），显著降低 MySQL fsync 压力，是 10K 消息吞吐达标的关键。

| G-01 | 我加入的群组列表 | P0 | ✅ | 💡 | `GET /api/groups` |
| G-02 | 创建群组（群主为创建者） | P0 | ✅ | 💡 | `POST /api/groups` |
| G-03 | 群组详情（含成员数） | P0 | ✅ | 🔧 | `GET /api/groups/:id` |
| G-04 | 群主解散群组（事务删成员 + 群） | P0 | ✅ | 🔧 | `DELETE /api/groups/:id` |
| G-05 | 加入群组 | P0 | ✅ | 🔧 | `POST /api/groups/:id/join` |
| G-06 | 群成员列表 | P0 | ✅ | 💡 | `GET /api/groups/:id/members` |
| G-07 | 添加群成员 | P1 | ✅ | 💡 | `POST /api/groups/:id/members` |
| G-08 | 移除群成员 | P1 | ✅ | 💡 | `DELETE /api/groups/:id/members/:member_id` |
| G-09 | 主动退群 | P1 | ✅ | 💡 | `POST /api/groups/:id/leave` |
| G-10 | 群公告 / 群管理角色（管理员） | P2 | ⚪ | — | 未实现 |

**设计要点（最终确定版）**
- `group_members` 表使用**联合主键（group_id + user_id）**，无单独 `id` 列，成员存在性以 `user_id` 判定。
- 群组解散、退群等涉及多表的操作置于数据库事务内，保证一致性。
- `groups` 为 MySQL 保留字，SQL 中统一反引号转义。

## 六、实时通信（WebSocket）

| 编号 | 功能点 | 优先级 | 状态 | 来源 | 端点 / 入口 |
|---|---|---|---|---|---|
| W-01 | WebSocket 连接鉴权（Token 升级） | P0 | ✅ | 💡 | `GET /ws`（Upgrade） |
| W-02 | 单聊消息实时推送 | P0 | ✅ | 🔧 | WS 推送帧 |
| W-03 | 群聊消息实时广播 | P0 | ✅ | 🔧 | WS 推送帧 |
| W-04 | 多端同时在线（同用户多设备不互踢） | P0 | ✅ | 🔧 | 内部 |
| W-05 | 心跳保活（Ping / Pong） | P0 | ✅ | 💡 | 协议层 |
| W-06 | 认证成功即时回执 | P0 | ✅ | 💡 | WS 推送帧 |
| W-07 | WS 连接统计（在线用户数） | P1 | ✅ | 💡 | `GET /api/ws/stats` |
| W-08 | 消息只推送「在线设备」，离线不补偿 | P1 | 🟡 | 💡 | 见 M-07 |

**设计要点（最终确定版）**
- 连接管理：每个连接分配全局唯一 `conn_id`；同一 `uid` 可挂载多个 `conn_id`（参考 OpenIM / WuKongIM 网关层模式），断线只移除自身通道，不顶替其他设备。
- 推送链路统一：REST 发送与 WS 发送**共用** `push_to_user` / `push_to_group`，保证多渠道一致。
- 协议层回执（Pong）与业务推送在独立任务中写出，避免 socket 写半边被多线程争用。
- WS 发送路径必须显式携带 Snowflake 预生成的 `id`，否则因线上 `messages.id` 无自增而插入失败（🔧 已修复）。

## 七、平台与运维（Platform & Ops）

| 编号 | 功能点 | 优先级 | 状态 | 来源 | 端点 / 入口 |
|---|---|---|---|---|---|
| O-01 | 健康检查 | P0 | ✅ | 💡 | `GET /health` |
| O-02 | 系统状态（DB 池 / 在线数 / 信号量） | P0 | ✅ | 💡 | `GET /status` |
| O-03 | 接口限流（Redis 滑动窗口 / 内存兜底） | P1 | ✅ | 💡 | 中间件 |
| O-04 | 跨域（CORS）放行 | P1 | ✅ | 💡 | 中间件 |
| O-05 | 连接池分离（读池 / 写池）+ 写并发信号量 | P0 | ✅ | 🔧 | 内部 |
| O-06 | 消息异步批量落库 | P0 | ✅ | 🔧 | 内部（可配置） |
| O-07 | 分布式就绪（AnyPool 多库 + Redis 抽象） | P1 | 🟡 | 💡 | 内部 |
| O-08 | 熔断器（接口级） | P2 | ⚪ | 💡 | `circuit_breaker.rs` 已实现未接入 |
| O-09 | 结构化日志（JSON / 可观测） | P1 | ✅ | 🤝 | 内部 |

**设计要点（最终确定版）**
- `/health` 返回 `status/version/uptime/timestamp`，供探针调用。
- `/status` 暴露读/写连接池的 `in_use`、`idle`、`sem_available`，是定位连接泄漏的关键观测点（压测后 `read_in_use=0` 即判定零泄漏）。
- 连接池最终确定：读池 300 / 写池 500（上限 800，按 `max_connections` 80% 配置），写并发信号量容量与写池一致（500）。
- 限流中间件读取 `RATE_LIMIT_RPM` 环境变量优先于 `config.yaml`，便于压测临时放开。
