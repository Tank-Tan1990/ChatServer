# ChatServer 功能实现说明

> 产品设计视角 · 各功能的最终实现路径、关键设计决策与已知约束
> **说明**：本文档描述**最终确定版**实现，不罗列中间迭代过程。每项注明设计理念的奠基工具（💡 QClaw）与定稿/修复工具（🔧 WorkBuddy）。所有描述基于当前代码实现，未涉及任何代码修改。

---

## 一、账号与认证

### 1.1 注册（A-01）
- 入参：用户名、密码、昵称（可选）。
- 流程：校验用户名唯一性（读池 `fetch_all`，规避 `fetch_optional` 连接泄漏陷阱）→ Argon2id 哈希 → 写用户表。
- 安全：密码不落明文；重复用户名返回 **422**。

### 1.2 登录与双 Token（A-02 / A-03 / A-04）
- 登录成功签发 **Access Token**（2h）与 **Refresh Token**（7d），响应为顶层 `{token, refresh_token}`。
- JWT 使用 `jsonwebtoken` HS256，claims 含 `sub=user_id`、`exp`、`iat`。
- 密码校验为 CPU 密集型，置于 `spawn_blocking` + 信号量（默认 300 permit）中执行，避免阻塞 Tokio worker。
- 登录态更新、旧密码哈希迁移改为后台 `tokio::spawn` 异步执行，不阻塞响应。

### 1.3 凭证携带（A-05 等通用）
- 统一 `AuthUser` 提取器（`src/api/extractors.rs`）：支持 `Authorization: Bearer` 与 `?token=` 两种形态。
- 全部受保护接口经此提取器鉴权，无需在每个 handler 手动解析。

> 🔧 WorkBuddy 定稿：Argon2id 可调档 + 登录校验 `spawn_blocking` 信号量 + 旧哈希透明迁移，是登录 10K 并发达标的关键。

## 二、好友关系

### 2.1 好友申请与处理（F-02 / F-04）
- 申请落 `friend_requests` 表；处理时读真实 `request_id`（列表字段为 `request_id`，非 `id`）。
- 同意：双向写入 `friends` 关系。拒绝：删除申请记录。

### 2.2 已知约束
- 无好友备注、分组（F-06 未实现）。

---

## 三、消息系统

### 3.1 发送消息（M-02）
- 单聊：`receiver_id` 非空、`group_id` 为空。群聊：`group_id` 非空、`receiver_id` 为空。
- 消息 ID 由 `Snowflake` 在应用层预生成（`src/snowflake.rs`）。
- 落库策略：
  - 默认同步 `INSERT`；
  - `MESSAGE_ASYNC=1` 时进入内存通道（`src/message_writer.rs`），由 3 个后台 worker 每 50ms 或满 500 条做事务批量写入——把 N 次 fsync 压缩为 1 次，显著提升写吞吐。
- 推送：写库后构造统一推送 JSON，单聊走 `push_to_user`（接收者 + 发送者其他设备），群聊走 `push_to_group`。

### 3.2 历史与已读（M-01 / M-03 / M-04）
- 历史消息分页查询，支持会话维度过滤。
- 已读标记更新消息 `is_read` 状态。未读计数聚合查询。

### 3.3 已知约束
- 离线消息无独立补偿机制：仅向在线设备推送，离线用户在下次上线拉历史时获得完整消息。
- 消息类型目前以 `text` 为主，结构已预留。

## 四、群组系统

### 4.1 创建与解散（G-02 / G-04）
- 创建：`owner_id` 写入群主，初始成员含创建者。
- 解散：事务内删除 `group_members` + `groups`，仅群主可执行。

### 4.2 成员管理（G-06 ～ G-09）
- 加入、添加成员、移除成员、退群均维护 `group_members` 联合主键关系。
- `groups` 为 MySQL 保留字，SQL 中统一反引号转义。

### 4.3 已知约束
- `group_members` 表无 `id` 列，成员存在性判定依赖 `user_id`。
- 无群公告、管理员角色细分（G-10 未实现）。

## 五、搜索能力

### 5.1 实现（S-01 / S-02）
- 模糊匹配：`LIKE '%keyword%'`，上限 20 条。
- 用户搜索排除自己；群搜索返回群名、描述、群主等信息。需登录调用。

## 六、实时通信（WebSocket）

### 6.1 连接与鉴权（W-01 / W-06）
- `GET /ws` 经 `WebSocketUpgrade`；鉴权 Token 在升级时校验 `decode_token`。
- 鉴权成功即向本连接推送 `auth_success` 帧。

### 6.2 多端在线（W-04）
- 连接管理采用 `uid → {conn_id → Sender}` 两层映射（参考 OpenIM / WuKongIM 网关层）。
- 断线只移除自身 `conn_id` 通道，不影响同用户其他设备。

### 6.3 推送链路（W-02 / W-03）
- 协议层回执（Pong）走 `out_tx` mpsc 通道，`send_task` 统一写出。
- 业务推送统一 `push_to_user` / `push_to_group`，REST 与 WS 发送路径共享。

### 6.4 心跳（W-05）
- 收到 `Ping` 回 `Pong`，维持长连接存活。

### 6.5 已知约束
- WS 写库的 `messages.id` 必须显式指定（Snowflake 预生成），否则因线上无 `AUTO_INCREMENT` 而失败（🔧 已修复）。

## 七、平台与运维

### 7.1 连接池与并发控制（O-05）
- 读写分离：读池 300 / 写池 500（默认上限 800，按 `max_connections` 的 80% 配置）。
- 写操作经 `Semaphore` 限并发（容量 = 写池容量 500）+ `spawn_blocking`，保护连接池不被 CPU 密集任务挤占。
- 读池与写池通过 sqlx Pool 内部 `Arc` 共享底层连接，避免历史上「三池超卖超过 MySQL 上限」的连接耗尽。

### 7.2 限流（O-03）
- `DistributedRateLimiter`：基于 Redis 的分钟级滑动窗口（默认关闭，可由 `RATE_LIMIT_RPM` 临时放开）。
- `SimpleRateLimiter`：纯内存兜底，用于无 Redis 场景。
- 中间件 `rate_limit_middleware` 全局挂载。

### 7.3 可观测性（O-01 / O-02 / O-09）
- `/health` 探针；`/status` 暴露连接池 `in_use/idle` 与 `write_sem_available`。
- 结构化日志（JSON 格式），级别可由 `config.yaml` 或环境变量调整。

### 7.4 未接入项（O-08）
- `circuit_breaker.rs` 已实现熔断逻辑，但未挂入 API 层（避免改变请求行为），属于后续可选增强。

## 八、数据模型概要（最终确定版）

| 实体 | 关键字段 | 说明 |
|---|---|---|
| users | id, username, nickname, password_hash, avatar_url, status | 账号主体 |
| friends | id, user_id, friend_id, status | 双向好友关系 |
| friend_requests | id(request_id), from_user_id, to_user_id, status | 好友申请 |
| messages | id(Snowflake 预生成), sender_id, receiver_id, group_id, content, msg_type, is_read | 消息记录 |
| groups | id, name, description, owner_id, avatar_url | 群组主体 |
| group_members | group_id, user_id（联合主键，无 id 列） | 群成员关系 |
| refresh_tokens | id, user_id, token, expires_at | 刷新令牌 |

> 架构注记：代码保留了 `DatabaseType` + `SqlDialect` + `AnyPool` 的多数据库抽象层（💡 QClaw 构想），实际查询以手工 `try_get` / 类型转换走 MySQL；除 MySQL 外的其他库类型仅停留在设计/迁移脚本层面，未经验证。
